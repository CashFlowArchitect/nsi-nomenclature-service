# ADR 001: Нормализация исторических записей и функциональный индекс дедупликации

## 1. Статус
Принято

## 2. Контекст и проблема
В исторической базе ERP-системы накоплено около 17000 номенклатурных позиций крепежа. Технический аудит выявил критическую проблему качества данных: знак умножения в существующих записях введен хаотично:
* Кириллическая строчная буква «х» (`U+0445`);
* Латинская строчная буква «x» (`U+0078`);
* Типографский знак умножения «×» (`U+00D7`).

**Бизнес-ограничение:** Выполнение прямого SQL-скрипта массовой очистки данных в производственной базе было категорически заблокировано бухгалтерией и юридической службой: изменение исторических наименований затрагивает закрытые финансовые периоды прошлых лет, аннулирует контрольные суммы электронных накладных в системе ЭДО и ломает интеграцию с архивными заказами.

## 3. Рассмотренные варианты
* **Вариант 1. Полный ретро-клининг базы 1С:** Отклонен из-за юридических и налоговых рисков изменения данных в закрытых периодах.
* **Вариант 2. Проверка дубликатов через `LIKE %...%`:** Отклонен из-за деградации производительности: сканирование таблицы приводило к времени ответа API более 1.2 сек.
* **Вариант 3. Нормализация на стороне NSI API + функциональный индекс в SQL:** Выбранное решение.

## 4. Принятое решение
1. При проверке уникальности сервис NSI Core API на лету нормализует входящую строку, приводя все вариации символов «x» к единому стандарту `×` (`U+00D7`).
2. В СУБД создан уникальный функциональный индекс.

## 5. Последствия
* **Положительные:** 
  * Исторические закрытые периоды в ERP остались нетронутыми.
  * 100% защита от создания дубликатов при сохранении новых позиций.
  * Время проверки коллизии сократилось до < 2 мс.
* **Отрицательные:**
  * Накладные расходы на поддержание индекса при операциях `INSERT`.
  * Любой поиск по наименованию в БД обязан использовать выражение `LOWER(REPLACE(...))`, иначе стандартный B-Tree индекс не будет задействован оптимизатором запросов.
