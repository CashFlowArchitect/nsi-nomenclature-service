# ADR 002: Стратегия кэширования справочников ГОСТ в Redis
## 1. Статус
Принято

## 2. Контекст и проблема
Интерактивный интерфейс Мастер-фильтра генерирует высокую частоту запросов на чтение списков доступных параметров (`GET /api/v1/parameters/lengths` и `/coatings`). Прямое обращение к SQL при пиковой нагрузке (50+ одновременных инженера) приводило к избыточной нагрузке на пул соединений СУБД.

Требовалось реализовать слой кэширования. Полноценная "event-driven" инвалидация кэша через шину событий (при изменении матриц администратором НСИ) была оценена командой в 40 часов разработки, что превышало доступный бюджет MVP.

## 3. Принятое решение
Применен паттерн **Cache-Aside** со статической стратегией инвалидации по времени жизни (**TTL = 86400 сек**).
* Ключ кэша: `lengths:gost:{gost_id}:dia:{diameter_id}`.
* При промахе кэша сервис считывает данные из SQL и асинхронно записывает в Redis с флагом `EX 86400`.

## 4. Последствия
* **Положительные:**
  * Сокращение времени ответа эндпоинтов фильтрации с 45 мс до 1.8 мс.
  * Снижение нагрузки на CPU сервера SQL на 85%.
  * Экономия бюджета разработки за счет отказа от сложного механизма инвалидации.
* **Отрицательные:**
  * Задержка консистентности: если администратор добавит новый типоразмер в базу, пользователи увидят его в выпадающем списке только после истечения TTL (максимум через 24 часа). 
  * Риск официально согласован с ОГТ, так как государственные стандарты ГОСТ обновляются крайне редко. Для экстренных случаев предусмотрена ручная очистка кэша через Redis CLI (`FLUSHDB`).
