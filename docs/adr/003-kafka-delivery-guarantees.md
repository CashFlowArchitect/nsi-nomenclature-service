# ADR 003: Компромиссная стратегия доставки событий в Apache Kafka

## 1. Статус
Принято

## 2. Контекст и проблема
При сохранении номенклатуры возникает проблема распределенной транзакции: необходимо гарантировать, что запись зафиксирована в SQL и событие `NomenclatureCreated` успешно отправлено в Kafka.

Классический паттерн Transactional Outbox (запись события в отдельную таблицу БД и вычитка через Debezium CDC) требует развертывания Kafka Connect и усложняет инфраструктуру проекта на этапе пилота.

## 3. Принятое решение
Реализован синхронный двухфазный пайплайн с таблицей аварийного сброса (DLQ в СУБД):
1. Выполняется транзакция `INSERT INTO nomenclature` в SQL с коммитом.
2. NSI Core API синхронно отправляет событие в Kafka с параметром продюсера `acks=all` и 3 попытками повтора (`retries=3`, экспоненциальный backoff).
3. **Обработка сбоя Kafka:** Если после 3 попыток брокер недоступен, транзакция БД не откатывается (чтобы не терять созданный ID), а запись о сбое публикуется в локальную служебную таблицу `failed_events`.
4. Раз в час фоновый процесс проверяет таблицу `failed_events` и досылает неотправленные сообщения в Kafka.

## 4. Последствия
* **Положительные:**
  * Отказ от развертывания тяжеловесного стека Kafka Connect/Debezium на этапе MVP.
  * Нулевой риск потери мастер-записи в БД при падении брокера сообщений.
* **Отрицательные:**
  * При аварии брокера Kafka возникает временная задержка появления карточки в ERP/WMS до момента отработки фонового скрипта.
